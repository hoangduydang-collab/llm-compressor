Goal 06 / engineering field note · Planned · benchmark-gated

Packed NVFP4 W4A8 on Hopper

Run an official NVFP4 checkpoint on an H100 without unpacking it to FP8 first — keep the weights at four bits, convert fragments to FP8 inside the GEMM, and let Hopper's FP8 Tensor Cores do the multiply.

Design complete · prototype committed Zero hardware results yet Reuse Humming, not a clean-sheet kernel

Read this first No hardware has run yet

Everything below is design plus committed CPU-side prototype code and a ready-but-unrun executor packet. There are zero measured latency, memory, correctness, or WGMMA-instruction numbers. Any figure on this page is either an upstream fact or a design-time arithmetic bound, and is labelled as such. The one-layer GPU probe is the immediate next task.

01 / MotivationRelease-day compatibility, without paying twice for memory

Official model releases increasingly ship NVFP4 checkpoints intended for native Blackwell FP4 execution. Hopper has FP8 Tensor Cores but no native FP4 multiply — so the checkpoint arrives in a format the hardware can't natively run.

The obvious workaround — expand the four-bit weights to FP8 at load time — nearly doubles persistent weight memory and throws away the format's principal bandwidth advantage. The goal instead is to load an official NVFP4 checkpoint without offline conversion, keep weights packed at four bits in GPU memory, convert only the needed weight fragments to FP8 inside the GEMM, and perform FP8 Tensor Core multiplication.

Two framing constraints: this is both a release-day compatibility/performance investigation and a stronger comparator for our in-house W4A8 than a weight-only A16 fallback would be. And it must not weaken the reliable upstream W4A16 compatibility path — anything that doesn't fit the specialization routes back to Marlin.

Sources: docs/superpowers/specs/2026-07-19-hopper-packed-nvfp4-w4a8-fallback-design.md (motivation, non-goals); PROJECT_GOALS.md (goal 6).

02 / Engineering gapThe block-scale problem

Hopper (SM90) lacks native FP4 Tensor Cores. What upstream vLLM already gives us on Hopper:

  • Loads NVFP4 packed E2M1 weights + per-group E4M3 scales + a global scale, and repacks them for Marlin W4A16 (weight-only four-bit, higher-precision activations).
  • Vectorized E2M1→FP16/BF16 conversion, plus an E2M1→E4M3 register conversion primitive.
  • Dynamic per-token FP8 activation quantization.

What is missing is a packed-weight NVFP4 W4A8 path that does in-kernel E2M1→FP8 conversion feeding SM90 FP8 WGMMA. Two candidate reuse paths each fall short:

Why the two obvious reuse paths don't fit
CandidateWhy it doesn't fit
vLLM Hopper CUTLASS W4A8Accepts uniform signed INT4, group size 128 — not NVFP4 E2M1, group size 16.
Marlin FP8 mma.syncBuilt only for SM89/SM12x; on SM90 it's simulated through FP16 MMA and does not accelerate Hopper. A useful path needs an SM90 WGMMA mainloop.

The crux: two group-16 scales inside one K=32 WGMMA step

The closest machinery is the Humming backend (humming-kernels==0.1.10, pinned by upstream vLLM): E4M3 activations × packed E2M1 weights on SM89+, compact group scales, global scales, dynamic input quant, WGMMA. But its FP8 path cannot apply two NVFP4 group-16 scales inside one K=32 WGMMA step — HummingKernel.check_scale requires every weight-scale group to be at least the MMA-K quantum 256 / activation_bits = 32, while NVFP4's group size is 16. The precise missing mechanism: each K=32 WGMMA weight fragment must load two E4M3 scales, apply each to its 16-wide half after E2M1→E4M3 register conversion, then issue FP8 WGMMA.

Sources: design spec (upstream inventory, INT4-vs-E2M1 mismatch, Marlin SM90 simulation, Humming check_scale group-quantum constraint).

03 / EffortExtend Humming first; clean-sheet only if forced

An initial two-reference audit appeared to show no packed NVFP4 W4A8 path anywhere — but a broader upstream search found one inside the Humming backend. That reversed the plan: extend and qualify the existing Humming W4A8 path first; a bespoke CUTLASS kernel is authorized only if the Humming specialization is absent or fails a predeclared correctness, memory, or performance gate. (A textbook application of the repo's search-first prime directive.)

The chosen mechanism

A bounded “group-16 specialization”: expand the existing scale-register path so a WGMMA N16 subblock carries the extra E4M3 scales, apply each scale to its 16-wide converted half while the weight is still in E4M3 registers, and disable Humming's ordinary post-accumulator group scaling for that policy. The numerical contract is fixed:

# in-GEMM weight conversion, with /8 headroom
B8 = Q_E4M3( E2M1(B4) * group_scale / 8 )

# max finite product 6*448/8 = 336 stays inside E4M3 range;
# a single compensating (global_scale * 8) is applied outside the GEMM.

The first specialization accepts only one scalar B_global_scale shared across fused projections; anything else routes to Marlin. The environment is frozen (vLLM 0.24.0 from toncao/vllm@minimax-m3-compressed-tensors; Humming tag commit pinned with SHA-256 hashes for the six target source files). A full custom SM90 CUTLASS E2M1 W4A8 datatype variant is fully mapped as a contingency, entered only after a concrete Humming blocker.

04 / ProgressCommitted prototype, nothing measured

The executor packet is in state READY_FOR_EXECUTOR; the one-layer SM90 probe has not been run, and pipeline/results/hopper_nvfp4_w4a8/ does not exist. What has been produced is CPU-side planner code, committed to duy-branch (commit 8e0456a1):

  • A pure-Python bit-exact NVFP4→E4M3 reference and memory-accounting oracle — pipeline/hopper_nvfp4_w4a8/reference.py.
  • A fail-closed, idempotent six-file Humming source overlay + installer — pipeline/hopper_nvfp4_w4a8/humming_patch.py, pipeline/slurm/patch_humming_nvfp4_w4a8.py, install_humming_nvfp4_w4a8.sh.
  • Torch-free opt-in preflight decision logic that rejects any non-matching case to backend=marlin_w4a16 — pipeline/hopper_nvfp4_w4a8/preflight.py.
  • A one-layer GPU probe (N=128, K=128, M∈{1,8,32}) and its srun launcher — gpu_probe.py, run_hopper_nvfp4_w4a8_probe_srun.sh.
  • CPU contract tests (four pipeline/tests/test_*hopper_nvfp4_w4a8*/*humming* files) and the executor packet HOPPER_NVFP4_W4A8_HANDOFF.md.

The only concrete numbers so far are analytical

A design-time memory calculation shows the contingency's temporary eight-way scale pack would cost ≈1.0 byte/weight vs ≈0.5625 byte/weight for compact NVFP4 (4-bit weight + one E4M3 scale per 16) — roughly 1.78×, which would fail the 1.10× memory gate. These are arithmetic bounds in the design, not benchmark measurements.

Planned comparison targets (not yet measured): upstream NVFP4 W4A16 Marlin (compatibility + quality baseline) and load-expanded W8A8 (a throughput ceiling / control — explicitly not a result the new path is required to beat).

05 / GatesThe benchmark that decides everything

Goal 6 is benchmark-gated by design — each stage has predeclared numeric gates, and failure stops the work rather than escalating it.

Immediate: one-layer SM90 Humming probe

One node, one H100, M∈{1,8,32}, srun only (no sbatch), no model download, no serving, no timing, no MoE. It passes only if:

  • exactly humming-kernels==0.1.10 with all six sources patched; device_capability == [9,0];
  • exact-emulation numerical match at rtol=0.01, atol=0.25, finite for every M;
  • K16 scale isolation holds; global scale multiplied by exactly 8; deterministic;
  • memory ratio ≤ 1.10 with no persistent FP8-expanded weight;
  • SASS contains FP8 WGMMA.MMA_ASYNC with E4M3 operands.

Stage 2: dense proof-of-concept continuation gates

For every supported shape and M∈{1,8,32,128,512,2048}: no NaN/Inf; cosine similarity ≥ 0.999 to the deterministic W4A8 reference; relative L2 error ≤ 0.02; deterministic; misaligned shapes select W4A16 first. Memory: persistent weight+scale bytes ≤ 1.10× the W4A16 Marlin representation. Performance: after warmup, median kernel latency ≥ 15% faster than W4A16 Marlin in at least one decision-relevant M bucket and no more than 10% slower in the primary serving bucket.

The stop rule

If correctness or memory fails → stop. If correctness and memory pass but the performance gate fails → retain the prototype and evidence, but do not begin fused-MoE production work. Only a clean sweep continues.

Sources: design spec (probe gates, Stage-2 continuation gates, stop rule); HOPPER_NVFP4_W4A8_HANDOFF.md (probe scope & gates).

06 / Future workStaged path

  1. Run the one-layer SM90 probe (the one active, ready packet). Decision: does the patched Humming A8/E2M1/group-16 specialization compile on SM90 and satisfy the scale-isolation, numerical, memory, and WGMMA-instruction gates?
  2. Stage 2 — dense PoC: qualify across all shapes and M buckets against the continuation gates above; apply the stop rule.
  3. Stage 3 — dense serving qualification: only after Stage 2 — integrate behind an opt-in serving setting and compare W4A8 vs W4A16 Marlin vs load-expanded W8A8 (throughput, ITL, TTFT, peak HBM, startup) under the repo's fail-closed evaluation-harness contract, with a predeclared paired tolerance and no conflation with public benchmark scores.
  4. Stage 4 — MoE / productionization: fused MoE, expert parallelism, routing, gate/up fusion, broader model families — out of scope until Stages 2 and 3 pass; receives a separate spec.
  5. Contingency: the custom SM90 CUTLASS E2M1 W4A8 datatype variant — only if Humming fails a gate; its genuinely novel work is narrowly the E2M1→E4M3 converter and the compact group-16 scale feed.

Sources: design spec (“Staged execution and continuation gates”); implementation plan (post-probe boundary); HOPPER_NVFP4_W4A8_HANDOFF.md.
