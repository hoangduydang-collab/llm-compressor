01 / ObjectiveThe goal

The hard part of automatic quantization is not selecting four bits instead of sixteen. It is making a new model architecture, a quantization algorithm, and an inference engine agree on the same contract.

Our fork of llm-compressor is becoming the control plane for that agreement. The intended outcome: supply a newly released model, request one or more target algorithms and formats, and receive candidates that have passed structural, runtime, and quality checks.

Q / 01

Can the model representation satisfy the quantizer's expectations?

Q / 02

Did the intended transformations execute across the intended layers?

Q / 03

Does the checkpoint satisfy the inference engine's loading contract?

Q / 04

Does served behavior remain acceptable against a paired baseline?

A checkpoint can be structurally valid but low quality. It can be numerically healthy but exported under the wrong names. It can even load while silently misclassifying model components. We need separate evidence for each boundary.

02 / Problem 1The compatibility gap

New model releases regularly arrive before every quantization framework and inference backend has an explicit architecture profile. LLM Compressor supports GPTQ, AWQ, W4AFP8, NVFP4, MXFP4, FP8, and other schemes—but format support is not automatic architecture support. Supported upstream LLM Compressor capabilities

Boundary A · Before quantization

Adapt the model to the quantizer

The source model's configuration and module representation must satisfy the selected algorithm: targets, ignores, fused layouts, group sizes, AWQ smooth/balance mappings, GPTQ weighted targets, custom norms, and MoE expert representation.

AWQ uses activation statistics to identify salient channels and equivalent per-channel scaling to reduce weight-quantization error. That makes a wrong smoothing mapping an algorithm-specific failure, not a generic packing problem. AWQ paper

GPTQ uses approximate second-order information to quantize and compensate weights within a block. A layout working for GPTQ therefore does not prove that AWQ's smoothing path is correct. GPTQ paper

Boundary B · After quantization

Adapt the checkpoint to the runtime

The inference engine is the fixed target. Our export or repair path must align module names, ignored components, packing, scales, metadata, and layout with the loader.

The post-quantization gate checks whether the saved checkpoint's metadata and tensors match what the inference engine expects: module names, ignored components, packing, scales, target declarations, and loading policy must agree. Completing a quantization job is not proof that these checks will pass.

03 / CenterpieceThe three-layer pipeline

Static gates eliminate incompatible work. Embedded probes stop unhealthy all-layer runs. Full calibration proceeds only after the production path has survived both.

Static compatibility

Cheap checks at both boundaries. Unknown models or formats must fail as unsupported, never silently pass.

All-layer live probes

Production-shaped smoke quantization verifies coverage, mapping execution and numerical health before hours are spent.

Full acceptance

Full calibration, the post-quantization gate, runtime health and paired quality evidence form one acceptance chain.

Why the canary changed

The representative-layer canary is no longer the primary path. Isolating a layer can accidentally change tracing or lifecycle behavior and turn the harness into a confounder. The guarded replacement uses all layers with a smaller calibration workload, then verifies that targets partition, mappings complete, intended modules receive calibration, scales stay healthy, and progress is durable.

The checkers are MiniMax-M3-first, not universal. The target architecture is a model-agnostic orchestrator backed by explicit, versioned model-family and storage-format profiles.

05 / Problem 2Multimodality

Text and non-text token streams can have materially different activation distributions and sensitivity to quantization error. Recent vision-language quantization research reports this calibration mismatch between visual and text tokens. Supported upstream VLM calibration study

A robust multimodal path will need modality-aware samples, processor artifacts, placeholder/token alignment, and evaluations that actually exercise each modality. We are hardening the text path first. Multimodal calibration is deferred rather than implied by the current gates.

06 / Problem 3Official-checkpoint fallback

Official NVFP4 checkpoints are useful memory and quality baselines when reproducing the original recipe is expensive. On Hopper, the relevant vLLM execution path is FP4 Marlin.

FP4 Marlin on Hopper

vLLM's FP4 Marlin path supports weight-only FP4 execution on SM80+ hardware, including Hopper. It consumes packed FP4 weights with higher-precision activations. That is best described as an NVFP4-weight / A16-style execution path—not a runtime checkpoint conversion. Four-bit storage and weight-bandwidth benefits remain, but Hopper does not gain Blackwell's native NVFP4 Tensor Core path.

Supported upstream vLLM FP4 Marlin API · hardware compatibility · NVIDIA CUDA release notes

vLLM also exposes a separate utility that dequantizes NVFP4 back to a higher-precision dtype. It helps compatibility and diagnostics, but it is not a fast W4AFP8 compute path. NVFP4 emulation API

Proposed work Investigate load-time adaptation of an official NVFP4 checkpoint into a Hopper W4AFP8/W4A8 path: retain four-bit weight storage, use FP8 activations, and measure the quality trade-off. vLLM contains a compressed-tensors W4A8-FP8 scheme, but we found no official direct conversion from arbitrary NVFP4 checkpoints. Block-scale semantics make this more than a cast; the work likely needs a loader/repacking adapter and possibly a custom kernel or integration.

This would be a stronger comparator for in-house W4AFP8 than a weight-only A16 fallback. It is specialized systems work, so feasibility should be reviewed with colleagues who have kernel expertise before implementation.

07 / DirectionNear-term plan

  1. Run all-layer smoke quantization with embedded probes to qualify each recipe before committing to a full-calibration run.
  2. Run full-calibration quantization for qualified recipes to produce working in-house MiniMax-M3 checkpoints, starting with repaired GPTQ and a healthy AWQ path.
  3. Export each candidate through a versioned MiniMax-M3/runtime compatibility profile.
  4. Compare against BF16, the external AWQ control, and relevant official checkpoints with identical prompts, corpora, manifests and runtime settings.
  5. Report quality, memory, and throughput separately. Loading is not quality; checkpoint size is not compute speed.
  6. Generalize one model family and storage format at a time, backed by valid and corrupted fixtures.

The longer-term product is model-agnostic orchestration backed by explicit compatibility knowledge—not a universal checker that guesses.
