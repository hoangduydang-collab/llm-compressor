Goal 01 / engineering field note · Work in progress

Fast parallel quantization

The 30-hour calibration was never a compute problem. It was seven idle GPUs and one busy core. The fix already lived in the fork — it was simply never switched on.

Target: full run in 4–8 h AWQ + GPTQ MiniMax-M3 · ~450–460B params

01 / MotivationWhy speed matters here

A quantization run that cannot finish inside its wall-clock window produces nothing. A partially quantized checkpoint is not a smaller model — it is an unusable one.

The trigger was concrete. Two in-house AWQ full-calibration runs were cancelled after roughly half-completing in about 15 hours: they projected ~27–34 hours of total work against only ~9 hours of remaining wall-clock, so they could never land a complete checkpoint. The target is therefore a full quantization process in 4–8 hours, for both AWQ and GPTQ.

The reason it was slow is the important part. The slowness was wasted hardware, not necessary compute:

  • Only 1 of 8 GPUs was used. The production config ran a single python -m pipeline.run process with device_map: null. Calibration streamed one layer to one GPU while the other seven sat idle.
  • Experts were quantized serially. AWQ/GPTQ looped over 128 experts per MoE layer one at a time, and each narrow expert GEMM underutilizes an H100 — the fine-grained-MoE small-op pathology.

The scale that makes this expensive: MiniMax-M3 is roughly 450–460B parameters (~920 GB in bf16), 60 layers (dense 0–2, MoE 3–59), hidden size 6144, 128 experts per MoE layer — about 7.25B params (~14.5 GB bf16) per MoE layer.

Sources: PROJECT_GOALS.md (goal 1); M3_QUANT_SPEEDUP_PLAN.md — pain trigger & cancellation (decision log, 2026-07-14), one-GPU / serial-expert diagnosis, model-scale notes.

02 / Engineering gapWiring, not a missing algorithm

The conclusion reached on 2026-07-14 was blunt: use the built-in distributed calibration and stop bespoke work. Multi-GPU calibration for both AWQ and GPTQ already exists in this fork — it was simply never switched on, because runs launched as a single process, so is_distributed() returned False and every distributed branch stayed dormant.

The gap was integration and launch wiring, not a new parallel algorithm. Concretely, what was missing:

  • pipeline.run did not initialize compressed-tensors distributed state, so a torchrun launch alone left the distributed branches inactive.
  • The calibration dataset needed deterministic rank-local slicing; the inherited sampler could index the unsliced dataset and overlap work across ranks.
  • Multi-rank metrics, metadata, and completion needed ownership rules while collective checkpoint ops stayed collective.
  • MiniMax-M3's composite VL/MoE load exposed three upstream integration gaps: a composite-config constructor keyword, an insufficient collective timeout during asymmetric loading, and post-load fused-expert linearization that duplicated shared storage.

The parallel algorithms that were already present

  • AWQ — data-parallel. _compute_best_scale all-reduces activation statistics across ranks (src/llmcompressor/modifiers/transform/awq/base.py).
  • GPTQ — module-parallel. compress_modules bin-packs modules across ranks, reduces Hessians to the owner rank, quantizes, and broadcasts back (src/llmcompressor/modifiers/gptq/base.py).
  • Memory. Distributed compressed-tensors offload keeps one shared CPU copy across ranks, so host memory scales with model size, not rank count.

Sources: M3_QUANT_SPEEDUP_PLAN.md (conclusion & gap list); M3_DISTRIBUTED_QUANT_SPEEDUP_HANDOFF.md; code paths in src/llmcompressor/modifiers/.

03 / EffortA detour, then the prime directive

The instructive part of this goal is the mistake. A bespoke expert-parallel / expert-scatter implementation (pipeline/expert_scatter.py, pipeline/ep_moe.py, pipeline/bench_expert_scatter.py) was built and CPU-tested before we discovered the built-in path already existed. Those files are correct but shelved for reference only.

Observed in this fork The detour came from two unchecked assumptions

A misread version string (0.1.dev… is a setuptools-scm fallback, not evidence of being behind upstream) and an unverified memory fear — the “8×920 GB = 7.4 TB host RAM” worry that motivated the bespoke design turned out to be wrong. The corrective is the repo's prime directive: search reputable sources and read our own code before building.

The “search first” check surfaced strong prior art: MoE-Quant (IST-DASLab) quantizes DeepSeek-V3/R1 671B with GPTQ in ~2 h on 8×H100; llm-compressor v0.10 ships DDP for AWQ (2.9–3.2× on 4 GPUs) and GPTQ (3.8× on 4 GPUs; “3.9 h → 1 h” on Qwen3-30B-A3B); GPTQModel v6.1 reports 80%+ time reduction; and cyankiwi already published a working MiniMax-M3-AWQ-INT4 with standard tooling.

What we adopted

Extend the existing pipeline.run path exactly like the fork's DDP examples: (1) initialize compressed-tensors distributed state before model load when WORLD_SIZE>1; (2) load via load_context() with device_map=auto_offload; (3) partition the calibration set into disjoint rank-local datasets before oneshot; (4) keep metadata/metrics rank-safe while preserving collective saving; (5) launch as one top-level srun --gres=gpu:8 wrapping one torchrun --nproc_per_node=8.

Entry points: pipeline/distributed.py (DistributedContext.from_environment, 8-hour process-group timeout), pipeline/calibration.py (partition_bounds, build_calibration_dataset_with_partition), configs minimax_m3_distributed_smoke.yaml / minimax_m3_distributed_awq_full.yaml, launcher pipeline/slurm/run_m3_distributed_quant_smoke_srun.sh.

Phase-1 bench: the thread-pool approach was a dead end

The serial one-GPU baseline took 116.98 s; a one-process thread-pool scatter took 132.97 s — a 0.88× “speedup” against an 8× ceiling, with Python setup accounting for 45% of the measured serial work. A v2 bench confirmed the pattern (serial 63.88 s vs thread 115.88 s, 0.55×). This is what redirected the effort to the built-in distributed path.

The scale audit showed real per-channel smoothing (norm ratios 0.46–0.89, compensation error 0.0025–0.0041, matching the known-good cyankiwi reference), with GPTQ as a negative control (norm unchanged, scale = 1.0). Full-calibration configuration & live status

The full recipe (minimax_m3_distributed_awq_full.yaml) uses 512 calibration samples × 2048 sequence length, data-parallel split 64/rank across 8 ranks, with device_map: auto_offload and a deliberately small CPU budget to force disk offload — a single-process full-calibration attempt had died at 63,122 memory segments against a vm.max_map_count of 65,530.

Observed in this fork The AWQ target landed: full run in 7 h 22 m (2026-07-20)

Run 20260720T060340Z-m3-ddp-awq-full-r5-deadchan completed the full 512×2048, all-57-MoE-layer AWQ quantization end-to-end in 7 h 22 m on one 8×H100 node (launch 06:03:40Z → controller exit 13:25:31Z: ~19 min load, 6 h 40 m calibration at ~7 min/layer, ~19 min save + in-line gates) — inside the 4–8 h target. The checkpoint passed every fail-closed gate (smooth-fold on all 57 layers, quant-verify + risk-layer dequant sampling), served coherent chat on single-node vLLM TP8, and cleared the Goal 2 official smoke eval (ready_for_production: true). The run carries the dead-channel smoothing-degeneracy fix (e87eef77) and the qparam-broadcast fix (25a0324d); both are upstream-contribution candidates.
