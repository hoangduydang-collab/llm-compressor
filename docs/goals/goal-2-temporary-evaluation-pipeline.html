Goal 02 / engineering field note · Work in progress

The temporary evaluation pipeline

A stopgap harness that answers one question well: does our quantized checkpoint hold up against other quants and against BF16 — on identical prompts, identical samples, identical decoding. The team's official pipeline now exists as its own repository; migrating MiniMax-M3 onto it is in progress.

4 checkpoints compared lm-eval-harness 0.4.12 · vLLM Paired fidelity, not leaderboard scores

01 / MotivationFidelity, measured the same way every time

Vendor evaluations use long completions, stochastic multi-trial sampling, and private harnesses. Reproducing a headline score is slow and noisy — and it is not the question we actually need answered.

The question this pipeline answers is paired quantization fidelity: how does our in-house checkpoint compare to alternatives when every checkpoint receives the same prompt rendering, the same exact examples, the same decoding settings, and the same scoring implementation? That is done with EleutherAI's lm-evaluation-harness on its vLLM backend. Model quality is explicitly the first deliverable.

It is deliberately minimal — a stopgap. Whole categories of evaluation are documented as deferred: vendor headline-score reproduction, an SGLang backend, serving throughput / latency / TTFT / memory sweeps, multimodal benchmarks (MMMU-Pro, Video-MME), and agentic benchmarks (SWE-bench, Terminal-Bench, tau2). Those belong to a later, fuller pipeline; this one exists to make trustworthy model-to-model decisions now.

What “temporary” means precisely

This harness — the llm-compressor pipeline/evalsuite — was the interim, deliberately-narrow paired-fidelity tool. The team's official evaluation pipeline now exists as its own repository, and migrating MiniMax-M3 onto it is work in progress (see §08). So “temporary” is now literal: this stopgap holds only until M3 runs on the official pipeline.

What the table supports — and what it does not

Read directionally: our in-house GPTQ (W4A8) tracks BF16 closely and stays within a few points on every task, while the external AWQ comparator degrades sharply, most severely on AIME25 (−37.8 pts) and GPQA (−17.7 pts). The official MXFP8 is the strongest quant here, roughly baseline-equivalent. But these are seeded subsets (N = 100 / 30) with wide confidence intervals; they are valid for model-to-model decisions, not as public-leaderboard scores.

Do not confuse harness eras

An earlier report recorded very different GPQA numbers (GPTQ 0.28 / AWQ 0.24) from a superseded r3 methodology — multiple-choice acc_norm, temperature=0, thinking disabled. The table above is the current r4 harness: generation-based, thinking on, three seeds. The two are not comparable; the r3 numbers are obsolete.

04 / TrustWhy these four are comparable

Because the four models were evaluated in separate runs, comparability is not assumed — it is proven by hash. Every run records the SHA-256 of its harness contract, sample manifest, eval config, tokenizer, chat template, and rendered prompt. A dedicated cross-run contract gate checks a candidate run against the reference root and passes only if all fields match byte-for-byte.

All four runs share identical values, and the MXFP8 and BF16 runs each passed the gate with zero mismatches against the paired-reasoning reference root:

06 / EffortMost of the work was keeping BF16 alive

The dominant blocker was not scoring — it was getting the unquantized BF16 baseline (which needs 2 nodes at TP16) to initialize and stay up. It took runs r48 through r50 to clear:

  • CPU starvation (r48). vLLM's Ray EngineCore hung at “Connected to Ray cluster.” On Slurm 21.08, srun steps with no --cpus-per-task bind each task to one physical core; the raylet's 192-worker prestart storm starved the driver. Fixed (r49, env-only) with SLURM_CPUS_PER_TASK=192 and RAY_enable_worker_prestart=0.
  • NCCL interface (r49→r50). 16-rank NCCL init failed because node hostnames don't route cross-node. Fixed with NCCL_SOCKET_IFNAME=intranet and GLOO_SOCKET_IFNAME=intranet.
  • Production relaunch defects (r50). An NCCL PG timeout mid-generation (mitigated by distributed_timeout_seconds: 3600), an alias-vs-resolved-task-name bug, and a stale driver-done Ray sentinel that killed reruns.
  • GPQA sample-checkpoint crash. A U+2028 line-separator character crashed the GPQA shard checkpoint; fixed in commit 703b605b, then the GPQA shard was re-run in isolation (the gpqa-rerun-r48 config).

The contract machinery itself — deterministic stratified sample manifests, tokenizer/chat-template/harness hashing, fail-closed smoke gates, the cross-run contract gate, and the srun launcher — was built and unit-tested.

Sources: M3_PRODUCTION_EVAL_HANDOFF.md (r48–r50 fixes); design doc (contract machinery); commit 703b605b.

Reproduction checklist

  1. Install the pinned venv (lm_eval 0.4.12, vllm 0.24.0, transformers 5.14.1, compressed_tensors 0.17.2a…).
  2. Stage all four checkpoints at the paths above.
  3. Run each matrix config (they share eval_config: eval_minimax_m3_reasoning_r4.yaml) via the srun launcher from tmux; BF16 needs the extra env exports.
  4. Confirm each run's run_manifest.json reproduces the six hashes pinned in §04; run m3_quality_eval contract-gate against the reference root.
  5. Read scores from models/<label>/shards/<shard>/aggregate.json (per-model comparable form). The merged report is not yet wired for four-way (see §05).

08 / What's nextThe official pipeline (in progress)

This field note describes the stopgap. The team's official evaluation pipeline now exists as its own repository (AICloud/benchmarks), and migrating MiniMax-M3 onto it is work in progress.

It is two pipelines joined at a shared reporting layer — performance (aiperf-driven: throughput, TTFT/ITL, $/Mtok) and quality — both talking to a self-deployed OpenAI-compatible endpoint (one model load feeds both). It is decoupled from quantization by design: the boundary is the HTTP endpoint, not a Python import, so it runs in its own repo and its own venv.

Its quality harness — not the same as the stopgap above

The quality suite is lm-eval v0.4.10 with the [api] backends, run against the served endpoint (not in-process vLLM), plus three layers the stopgap lacks: distribution-damage, reliability, and agentic.

Decoding is greedy (temperature=0), single seed; generative tasks route to /v1/chat/completions, multiple-choice to /v1/completions (loglikelihood, tokenized locally). The extra layers: distribution (flip-rate / top-k agreement / truncated KL vs baseline, from served top_logprobs), reliability (tool-call + structured-output error rates; unconstrained = model signal), agentic (SWE-bench Pro / Terminal-Bench / GAIA). Each suite emits a shared NormalizedResult; a reporting layer joins baseline+candidate into a SHIP / CAVEAT / NO_SHIP delta.

Its numbers will not match the table in §03

The official pipeline uses different tasks, greedy decoding, and loglikelihood MC scoring — versus the stopgap's GPQA / MMLU-Pro / AIME reasoning set, temp=1.0 three-seed generation, and flexible-extract. So its absolute scores are not comparable to the §03 table. Continuity would require adding the reasoning tasks to the official quality/general/tasks.py registry (they are not in its default set).

How M3 plugs in (WIP)

The two repos stay separate, coupled over the endpoint: serve the M3 checkpoint on a pinned patched vLLM 0.24.0 image (see the M3 serving recipe), point a benchmarks profile (configs/minimax/minimax-m3.sh) at it, and run python -m quality.orchestrator --profile minimax-m3. Status today:

  • Official quality suites are built and GPU-free-tested against a mock endpoint; general/agentic execution is cluster-gated and not yet run for M3 — the only committed result in that repo is a performance run for MiniMax-M2.5.
  • The reproducible M3 serving recipe (stable vLLM 0.24.0 + the W4A8 Python overlay) and a scaffolded M3 profile exist; a served endpoint, the benchmarks venv, and the three comparator profiles (BF16 / MXFP8 / cyankiwi AWQ) remain to wire up.

Sources: benchmarks/quality/{README,general/tasks.py,general/command.py,distribution/metrics.py,requirements.txt}; benchmarks/README.md; docs/m3-serving-recipe.md.
