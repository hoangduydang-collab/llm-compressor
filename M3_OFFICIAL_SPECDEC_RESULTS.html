MiniMax-M3 · EAGLE3 speculative decoding · SPEED-Bench

Speculative decoding is worth 1.2×–2.5× on our W4AFP8 M3 — and the tuning is workload-dependent, not universal

An off-the-shelf EAGLE3 drafter on our in-house 4-bit M3 reaches 341.6 tok/s single-user on code (2.50× the same node without it) but only 1.36× on creative writing. Three tuning axes decide where in that range you land: how deep to draft, which kernel runs the drafter, and whether the drafter is quantized. The first is the big one — up to ~12% on code; the other two are worth ~2–3% each and act on the same layer. Bottom line

Read this if you have thirty seconds

Speculative decoding is the single largest decode-speed lever we have found on M3 — larger than any kernel or quantization change in the perf report — and it costs nothing in output quality, because verification is exact. But the size of the win is set by what the model is writing, not by prompt length and not by load. Code and structured output draft easily (accepted length 3.8–4.2 tokens per step); creative writing does not (1.5–1.8).

That single fact drives every recommendation here: draft depth must be tuned per workload (k≈5–6 for code, k=2 for creative writing — the reference recipe's one-size k=3 is wrong for both), while the two drafter-cost levers are real but small, and they trade places as load rises.

Setup

The benchmark, the target, and the draft model

What speculative decoding does here

Each decode step, a small draft model proposes k tokens autoregressively; the full target then verifies all k+1 positions in one forward pass and keeps the longest prefix it agrees with. Output is distributionally equivalent to plain decoding, so there is no quality axis to report — only speed. The economics are one line:

ITL = step cost ÷ accepted length

Raising k raises both terms. It pays only while the fractional gain in accepted length beats the fractional rise in step cost — which is why the optimum moves with the workload, and why the two other axes (which attack step cost alone) are worth measuring at all.

Target and serving stack

The target is our own GPTQ W4AFP8 M3 with the ABI overlay and the patched Humming indexed 0.1.10 MoE kernel — the same serve-ready configuration the perf report benchmarks — on one 8×H100 node at TP8/EP8, vLLM 0.24.0, 131,072-token context, FP8 KV cache, prefix caching on. Across every arm on this page the only flag that differs is --speculative-config, and each arm carries its own in-window k=0 control, so no ratio is taken across windows.

Both tuning axes are same-node comparisons, which is stronger than same-window. Axis 1's entire code-tier sweep — every k, its control and its drift repeat — ran in one allocation on gpu-h113, and the creative tier likewise on gpu-h114; both axis-2 windows also ran on gpu-h113, which is what makes the noise floor above a genuine same-node floor. A useful accident confirms the two nodes are matched: their independent k=0 controls both measured 136.8 tok/s at concurrency 1. The supporting figures quoted for context — the 1.81× mixed-traffic number and the length × entropy grid — come from earlier windows that placed the control and speculative arms on different nodes of the same pool, so those carry this study's 1–2% node variance on top of their stated precision. They are 36–115% effects, so nothing turns on it, but do not read them as same-node.

Our 4-bit target does not handicap the drafter. EAGLE3 conditions on the target's hidden states, so quantizing the target could have cost acceptance twice over. Measured against the drafter's own published reference format (vendor MXFP8) on hash-identical prompts, accepted length differs by +0.56% on average and flips sign across cells — that is noise, not a penalty. Our stack is also 22–40% faster than MXFP8 in absolute terms in every cell, with and without the drafter.

The draft model

Inferact/MiniMax-M3-EAGLE3 @ 44cafa5a — a single-layer LlamaForCausalLMEagle3 head, hidden size 6144, full 200,064-token draft vocabulary, 6.53 GB in bf16. It loads in our vLLM with no code change. MTP was not an option: M3's config.json declares num_mtp_modules: 7 but neither the BF16 nor the vendor MXFP8 release ships a single MTP tensor.

Axes 1 and 2 are measured on the 4-bit drafter — an RTN INT4 weight-only (W4A16) quantization derived from Sebesky/MiniMax-M3-EAGLE3-RTN-INT4. Weight-only is the right choice rather than a limitation: the drafter sees one token per user per forward, so its activations are kilobytes and quantizing them would add work without saving bandwidth. Axis 3 shows that this choice is free in acceptance, which is what licenses using it as the baseline everywhere else.

Content domain is the dominant axis; prompt length is irrelevant

Accepted length moves +75% between the two tiers (1.78 → 3.11) — far more than output shape (+33%), temperature (+4%) or prompt naturalness (+1%). Over a 32× range of prompt length (1k → 32k) it moves by less than 0.05, and it is flat in concurrency from 1 to 64. EAGLE3's drafter conditions on the target's hidden state, not on retrievable prompt text, so there is nothing for a longer prompt to give it. Plan capacity by what your traffic writes, not by how long its prompts are.

Two caveats to carry

  • Not comparable to published SPEED-Bench scores. 42–56% of the public parquet is masked pending fetch through the vendor's own harness, so we stage and hash-gate the clean subset; the mixed tier is fully masked and absent. Serving stack, temperature and graph mode also differ from the vendor recipe. These numbers are valid for configuration-to-configuration decisions, which is all this page makes.
  • Output-budget censoring. At max_tokens 2048, 60% of low-entropy and 87–93% of high-entropy responses hit the cap, so these are not natural-stopping lengths. Ratios survive (censoring is within a few points between arms, and both arms emit the same token counts), but do not read per-tier response lengths off this data.

Axis 1 · draft depth

Every k in this section is measured on one node, with the default kernel assignment and the INT4 drafter, against a k=0 control in the same window; each tier's sweep ends by re-serving its first speculative configuration to measure drift. The reference recipe ships k=3. It is wrong for both tiers, in opposite directions.

Axis 1 verdict — tune k per workload; it is the biggest lever on this page

Per-position acceptance decays geometrically while marginal step cost decays only slowly, so the crossing point is sharp and set by content entropy: k≈5–6 for code and structured output, k=2 for creative writing. The recipe's one-size k=3 is simultaneously too shallow for one tier and too deep for the other, and correcting it is worth +2.4% per user on creative writing under load (measured within one window) and +11.7% on code at single-stream (k=3 → k=6, compared across two windows, so ±1–2% node variance applies). Either way it is several times what the remaining two axes are worth. If you route traffic by type, route k with it.

Axis 2 · drafter kernel

Which W4A16 kernel runs the drafter — and why the answer depends on load

The 4-bit drafter's 9 linears each get a kernel from vLLM's own chooser, and the default split is not uniform. Machete — the fast Hopper mixed-precision GEMM — requires output features divisible by 128, and TP8 gives the draft lm_head 200,064 ÷ 8 = 25,008 per rank, where 25008 % 128 == 48. So Machete takes 8 layers and the older Marlin takes lm_head — the one layer carrying 60% of the drafter's weight traffic. vLLM warns about the consequence directly: the padded layer's activations and outputs are "padded/sliced on every forward".

Four cells break that default apart, all at k=5 on the code tier, with the kernel assignment verified at serve time (kernel census gated fail-closed, so no cell can silently fall back). Acceptance is a control here, not a result: the drafter weights and prompt bytes are byte-identical across cells, so any acceptance movement is noise or a numerics bug.

Integrity note: our first reading of this axis was wrong, and the noise floor is why

The Machete-everywhere cell was originally dismissed as "not significant" — its +1.85% at concurrency 10 was compared against the concurrency-1 noise floor (sd 1.02%), the only floor measured at the time. The fourth replicate later put the concurrency-10 floor at sd 0.16%, roughly seven times tighter, which makes +1.85% about eleven standard deviations. It was significant all along. The conclusion published here is the corrected one: the conc-1 null stands, the conc-10 dismissal does not.

The mechanism is the conventional one. All three winning cells share exactly one feature: Marlin is off the lm_head at batch greater than one. Marlin was built for the memory-bound batch-1 regime, where it is at home and the assignment does not matter. At concurrency 10 the drafter GEMM has ~10 rows, and Marlin's weak batch scaling costs ~2–3% of the entire decode step through the layer holding 60% of the drafter's weight traffic. These cells cannot separate how much of that is the per-forward pad/slice versus Marlin's batch scaling — and nothing downstream needs the split.

Sized against the drafter rather than the whole iteration, the effect is larger than it looks. Drafting accounts for 12.77 of the 26.199 ms step at concurrency 10 (49%, taking the k=0 control as the no-drafting reference), so the −3.25% whole-step saving is −0.85 ms, or ~6.7% of the drafter's own cost. That is a plausible magnitude for a kernel change on one layer of nine; 3.25% of an entire decode iteration would not be.

Side finding: two upstream vLLM defects, one now fixed with a tested patch

Forcing Humming onto the draft lm_head initially killed all 8 ranks at weight load (AttributeError: 'ParallelLMHead' object has no attribute 'input_size'). vLLM's prepare_humming_layer re-derives shapes from three attributes only LinearBase sets, although the same code path also serves quantized ParallelLMHead layers — which is exactly how Marlin serves this layer today. The path was both unreachable by default and broken when reached. A ~10-line guarded-fallback patch fixes it; the two cells above are the first Humming W4A16 forward ever run through vLLM's mixed-precision linear path, and acceptance landing in the normal band is the numerics proof. The second defect, found earlier: vLLM builds the draft embedding without a quantization config, so a published quantized drafter cannot load at all (see axis 3).

Axis 2 verdict — two regimes

  • Single-stream / latency tier: leave the default. Every cell is inside the 1.02% noise floor. Moving 60% of the drafter's weight traffic off Marlin, and eliminating a per-forward pad/slice, produces no measurable change.
  • Loaded serving (conc ≈ 10): take Marlin off the drafter's lm_head. Best measured is VLLM_DISABLED_KERNELS=MarlinLinearKernel at +2.73% per user (requires the patch above). The patch-free alternative is padding the draft vocabulary to 200,704 so Machete claims the layer, at +1.85%.

Axis 3 · drafter precision

Quantizing the draft model — free in quality, small and real in speed

Axes 1 and 2 take the drafter's cost as given. This axis attacks it directly: the drafter is read in full on every one of the k forwards per step, so shrinking its weights should shrink the step. The instrument is an RTN INT4 weight-only (W4A16) quantization of the exact drafter already in use, A/B'd against bf16 on the same node inside the same allocation — serve INT4, run the grid, tear down, serve bf16, run the identical grid — across 12 cells (k=3/4/5 × both entropy tiers × conc 1 and 10).

Why the ceiling is low — and how this connects to axis 2

A bandwidth model predicted −4.3% of step cost at k=3 on the code tier; the measurement is −2.20%, roughly half. The explanation is that a drafter forward is not bandwidth-bound. It runs at three to four times its HBM floor, so only a quarter to a third of it is weight streaming; the rest is per-invocation cost — kernel launch, all-reduce, dispatch — that no weight format can touch. Cutting weight bytes by 4× therefore has a small ceiling by construction, and axis 2 tested the leading candidate for the rest of the gap.

The two drafter-cost axes act on the same layer and trade places with load. Both target the drafter's lm_head: axis 3 makes its weights smaller, axis 2 changes the kernel that reads them. Measured at the code tier's k=5:

The pattern is coherent with the mechanism. At concurrency 1 the drafter GEMM has a single row, so fewer weight bytes is exactly the right lever and Marlin is in the regime it was designed for. At concurrency 10 it has ten rows: the weight read is amortised across them, so precision matters less, while Marlin's weak batch scaling starts to cost real time. Honest caveat: these are two separate experiments, so the levers were never crossed in one factorial run. We cannot claim the savings add — only that each is real in its own regime, and that the two regimes are different.

Axis 3 verdict — adopt the 4-bit drafter, but do not expect much from it

It is free in acceptance (mean −0.21%, signs flipping), unanimously non-negative on step cost across 12 cells, and worth roughly +2.6% per user at the low-entropy deployment k at concurrency 1, falling to under 1% under load. Take it — it costs nothing and never hurts — but it is a minor lever: the same code workload gains +11.7% from moving k=3 → k=6, more than four times as much.

Getting there required repairing the published checkpoint

The public INT4 drafter does not load in vLLM: llama_eagle3.py builds the draft embedding without passing a quantization config while passing one to lm_head, so there is no packed-weight parameter to load into — KeyError: 'embed_tokens.weight_packed' on all 8 ranks. Quantizing that tensor could never have paid anyway: when the draft embedding matches the target's, vLLM deletes it and shares the target's table. Our preparation step restores the bf16 embedding, drops that quantization group, and carries the other 34 tensors byte-for-byte, asserted tensor-by-tensor rather than assumed.

If you can only make one change, make it k per traffic class. If you route by content type already, the two drafter-cost levers are cheap to add on top: the 4-bit drafter is a checkpoint swap that never hurts, and the kernel override is one environment variable that helps only under load.

Scope

What this page does not cover
  • Prefill-dominated traffic gets almost nothing. Speculation accelerates decode and never touches prefill. An agentic shape that emits ~100 output tokens per ~12k-token prompt is outside the regime where any of this pays.
  • Axes 2 and 3 were measured at k=5 on the code tier only. Neither has been re-measured at the creative tier's k=2, where there are fewer drafter forwards per step to save on. Expect less, not more.
  • Concurrency was 1 and 10 for the tuning axes. A separate sweep confirms speculation still pays at concurrency 16/32/64 (server throughput 1.95× / 1.97× / 1.79× at k=3), but the per-axis optima were not re-derived there, and both the noise floor and the k optimum are load-dependent.
  • The two drafter-cost levers were never crossed factorially, so their savings are not claimed to add.
  • Absolute accepted lengths reflect a censored output budget (2,048 tokens) and a staged clean subset of SPEED-Bench. Ratios are sound; leaderboard comparison is not.
