MiniMax-M3 · Quantization performance · aiperf

W4AFP8 decodes faster than every M3 provider but one — on half the hardware

Our in-house W4AFP8 quant serves at 137 tok/s single-user (second only to Nebius among commercial M3 endpoints), 3.8× BF16's reasoning output tok/s per GPU, and holds a 1-second agentic p95 TTFT SLO to concurrency 16 — same checkpoint we shipped, zero requantization. Results are organized on two axes: which kernel (model fixed) and which quantization (kernel fixed). Quality verdicts: M3_OFFICIAL_QUALITY_RESULTS.html; superseded results: M3_HISTORICAL_PERF_RESULTS.html.

Bottom line

Read this if you have thirty seconds

In-house W4AFP8 on one 8×H100 node, stock vLLM plus our patched Humming MoE kernel: 137 tok/s single-user decode (BF16: 81 on two nodes), 3,267 tok/s total output at concurrency 64 (BF16: 1,700 on twice the GPUs), a 1-second agentic p95 TTFT SLO held to concurrency 16, and 131 tok/s decode with a 100k-token prompt — the full serve-ready vs BF16 comparison is one table. Method

Two measurement paths, two comparison axes

aiperf 0.8.0 drives synthetic traffic against each arm's OpenAI endpoint; engine held fixed (vLLM 0.24.0, identical flags, FP8 KV cache, 131,072-token context). Quant arms: one 8×H100 node (TP8). BF16: two nodes (TP16/ray). Each axis reports both paths:

  • Primary path (suite-native) — reasoning: 1k input, 8k forced decode (ignore_eos; isolates kernel speed from model verbosity), temp 0.6, thinking on, concurrency 1/4/16/64; agentic: multi-turn, M3-calibrated tau2 shape — 8±2 turns per sticky session, prompt growing 8.1k → ~15k tokens as the transcript accumulates (mean 12k measured), only ~100 output tokens per turn — warm (KV reuse) vs cold (cache-defeated, single-turn 10.6k prompts), concurrency 1/4/16/32.
  • AA-style sweep — Artificial-Analysis axes: input 1k/10k/100k × concurrency 1/10, natural output length (AA's answer-token floors recorded, not forced). Comparable columns are output speed and TTFT; AA-style, not AA-leaderboard-comparable (synthetic prompts, model-tokenizer units, one batch vs their 72-h medians).

Table format everywhere: primary cells are TPOT p50 ms (total output tok/s); AA cells are output speed p50 tok/s (TTFT p50 ms). Cross-window TPOT noise floor is ±0.2% (re-run arms reproduce to ±0.02 ms). Provider numbers are matched on workload shape but carry live multi-tenant load — same-ballpark placement, not a ranking.

Metric definitions

What we reportaiperf fieldDefinition
TPOT p50 (ms)inter_token_latencyTime per output token in steady decode: (request latency − TTFT) ÷ (output tokens − 1). Lower is better.
output speed (tok/s)output_token_throughput_per_userOutput tokens per second for one request — exactly 1 ÷ inter-token latency, i.e. the decode rate a single user sees. Artificial Analysis calls this Output Speed; aiperf and NVIDIA's InferenceX plots label the same field interactivity. At concurrency 1 it is 1000 ÷ TPOT, the TPOT column inverted.
total output tok/soutput_token_throughputOutput tokens summed over all concurrent requests ÷ benchmark wall time — the figure in parentheses in the tables. Output tokens only, and prefill time is in the denominator, so it is the whole server's output rate rather than one stream's decode rate.
output tok/s per GPUderivedTotal output tok/s ÷ GPUs in the deployment (8 for every quant arm, 16 for BF16). The efficiency axis for cross-arm comparison.
TTFT (ms)time_to_first_tokenTime to the first streamed token — for M3 that is the first reasoning token. p50 unless p95 is named.
requests/srequest_throughputCompleted requests ÷ wall time. Recorded in every artifact; on the pinned-8k reasoning shape it is just total output tok/s ÷ 8,000, so the token form is what these tables show.
input + output tok/stotal_token_throughputNot reported here. aiperf records it in the raw exports, but prompt tokens are processed once at prefill while output tokens are generated one at a time, so mixing them hides the decode behaviour these comparisons are about. Every tok/s figure in this document counts output tokens only.

Definition table — no ranking, no highlights

How to read the highlights. One rule, applied to every table: the green fill marks the best cell in the row, and any cell within 1% of it is marked too (that is measurement noise, so co-leaders are shown as co-leaders). Every data row therefore carries at least one green. The amber left bar is a separate, composable mark: the cell misses the stated threshold for that table — for agentic tables, p95 TTFT above the 1-second TTFT SLO. A cell can be both (fastest arm, still over the SLO). Amber text with a † means the cell is not a valid comparison (cyankiwi's runaway generations); those cells are excluded from the row ranking. Tinted rows are baselines or our own arms, as noted per table. Three tables are not row-wise comparisons — the definitions table above, the kernel-stage narrative and the provider ranking — and each says so underneath.
