Why this is here

Two verdicts changed when the stack changed

These tables were the basis of the first "which checkpoint should we serve" decision. The kernel work that followed (axis 1) moved the in-house arms ~40% on single-user decode, so the absolute numbers below understate every quantized arm. Two specific conclusions from this window did not survive:

  • "MXFP8 and cyankiwi collapse at concurrency 4" — not reproduced on the current stack; both complete every concurrency now, they are simply the slowest arms.
  • The BF16 baseline was suspected of being ~7% low from a cross-window comparison — the re-run landed on the same 81 tok/s, so the caveat is closed.

What did not change: cyankiwi's quality verdict is still disqualifying, and the in-house arms still lead every operating point. Metric names follow the current report — total output tok/s = output tokens over all concurrent requests ÷ wall time; output speed = one request's decode rate. Highlights: green = best in row (±1%), amber bar = p95 TTFT over the 1-second SLO.
